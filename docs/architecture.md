# Architecture

How Workout Planner is put together, for anyone changing the code. For what the app does and how to
deploy it, see the [README](../readme.md).

## Overview

- **Backend:** FastAPI, with SQLModel on SQLite. One process, one database file.
- **Frontend:** a single page (`index.html`) with four views: Workout, History, Program and Profile.
  It mixes two styles:
  - the newer parts are plain JavaScript that render from JSON: the session wizard, history and
    program editor;
  - the older forms (log an exercise, load calculator, bodyweight) use
    [HTMX](https://htmx.org) and get HTML fragments from the server.
- **Styling:** [Pico CSS](https://picocss.com) with the app's own theme on top, and the Inter font
  bundled in `static/fonts/`.
- **Offline:** a service worker caches the app, and sessions are queued on the device until they
  can be uploaded (see [Offline](#offline)).
- **Auth:** Cloudflare Access sits in front of the app and adds a signed JWT to every request.
  `auth.py` verifies it against the team's public keys, and `get_current_user` in `app.py` creates
  the user on first sight.

## Files

| File | What it holds |
| --- | --- |
| `app.py` | All routes: HTMX fragments, JSON API, 1RM maths (`get_onerepmax`, `get_target_weight`), program and session logic |
| `models.py` | Database tables (see [Data model](#data-model)) |
| `database.py` | Engine, seeding of default movements, startup migration of older databases |
| `auth.py` | Cloudflare Access JWT verification |
| `movement_names.py` | Standard form for movement names, used when creating and renaming movements |
| `movements.py` | Renaming, merging and deleting movements, and finding a movement from an out-of-date name (shared by the app and the tool below) |
| `rename_movements.py` | Command-line tool that renames existing movements to the standard form |
| `index.html` | Page layout, all CSS, tab routing, theme switching, date and decimal field helpers, progress chart, HTMX forms |
| `static/workout.js` | Session wizard, History (cycle overview, sessions, trends) and the upload queue for sessions |
| `static/program.js` | Program editor, the movement picker, and renaming or deleting movements |
| `static/offline.js` | Registers the service worker, caches data in IndexedDB, replays offline writes from the HTMX forms |
| `sw.js` | Service worker: caching, plus offline answers for the HTMX endpoints |
| `manifest.json`, `static/*.png`, `static/logo.svg` | Home-screen install and icons |

`static/workout.js` exposes `window.WorkoutApp` (`getData`, `refresh`, `esc`, `fmt`) for
`static/program.js`. It also fires a `program-data` event on `document` whenever the program data
is (re)loaded.

## Data model

| Table | Key fields | Notes |
| --- | --- | --- |
| `user` | `email`, `bodyweight`, `is_admin` | Created on first login. Bodyweight is used for dip-belt movements. |
| `movement` | `name` (primary key), `dip_belt` | Shared by all users; only admins create or rename them. Names follow `movement_names.py`. |
| `movementalias` | `old_name` (primary key), `movement_name` | Former names of renamed movements. Phones may upload sessions recorded under an old name, so the server looks them up here (`movements.resolve_movement`). |
| `exercise` | `exercise_name`, `sets`, `reps`, `weight`, `rpe`, `bodyweight`, `created_at`, `session_id` | One logged exercise. `rpe` is optional. `bodyweight` is a snapshot, set only for dip-belt movements. `session_id` links it to a workout session, or is empty for one-off logs. |
| `workoutday` | `user_id`, `name`, `weekday`, `slots` (JSON) | A day of the program. Each slot is `{movements: [...], sets, reps, week_targets, rpe_targets}`. The movements are alternatives. `week_targets` has `{sets, reps}` for each week of the cycle when they change from week to week, or is null (or missing) when `sets` and `reps` apply to every week; when present, `sets` and `reps` equal week 1's. `rpe_targets` has one value per week of the cycle, or is null. Days saved by older versions may have a single value meaning "every week". |
| `workoutsession` | `client_id`, `user_id`, `day_id`, `day_name`, `cycle`, `week`, `date` | One performed workout day. `client_id` is generated by the browser, so uploads can be repeated safely. `day_name` is a copy, so history survives renaming or deleting the day. |

**Dates.** A session's date part is the day the user picked; its time is when it was first saved,
in UTC. The frontend uses only the `YYYY-MM-DD` part, so time zones don't shift sessions to another
day. Dates are shown as "4 Nov 2026" everywhere.

**Weights.** For dip-belt movements, `weight` is the load on the belt. The estimated 1RM
(`get_onerepmax`) is likewise the weight that could be added for a single rep, computed with the
bodyweight included.

## Migrations

There is no migration framework. `SQLModel.metadata.create_all` creates missing tables, and
`database.migrate_exercise_table` upgrades an `exercise` table from before sessions existed. It
makes `rpe` nullable and adds `session_id` by rebuilding the table, because SQLite can't drop a
NOT NULL constraint in place, and it copies the database file to `database.db.<timestamp>.bak`
first. Further schema changes should follow the same pattern: detect the old shape, back up, change,
and make a second run a no-op.

## Offline

There are two mechanisms, one per frontend style.

**Sessions (`static/workout.js`).**

- **Saving:** the session in progress lives in `localStorage` (`workout-active-session`). Each time
  an exercise is completed, the whole session goes into an upload queue (`workout-unsynced-sessions`)
  and is sent to `POST /api/workout-sessions`, which creates or replaces it by `client_id`.
- **Retrying:** uploads run one at a time, always sending the latest copy, so an older copy can't
  overwrite a newer one. Failed uploads are retried on the next save, on page load, and when the
  browser comes back online.
- **Renamed movements:** the server maps former names (`movementalias`) and other spellings of a
  name to the current movement, so sessions recorded before a rename still upload.
- **Deleted movements:** an exercise whose movement no longer exists is skipped, and the rest of
  the session is saved.

**HTMX forms (`sw.js`, `static/offline.js`).**

- **Writes:** when a POST or PUT to a non-`/api/` route fails, the service worker stores the action
  in IndexedDB (`pending`) and returns a fake success response. `offline.js` replays the queue
  through `POST /api/sync` on load and when the browser comes back online.
- **Reads:** for `GET /movements`, `/exercises` and `/bodyweight`, the service worker builds answers
  from the data that `GET /api/sync` cached in IndexedDB.

**Caching (`sw.js`).**

- **Network first, cache as fallback:** the page, `/static/*`, the manifest, `/api/program` and
  `/api/trends`.
- **Cache first:** files from CDNs.
- **Not intercepted:** writes to `/api/*`, so their callers see real failures. A fake success would
  make them drop data they think was uploaded.
- **When you add a static file:** list it in `STATIC_ASSETS` and bump `CACHE_NAME`, so it's
  available offline from the first visit.

## API

All routes need a logged-in user (Cloudflare Access).

**JSON:**

| Route | Purpose |
| --- | --- |
| `GET /api/program` | Everything the wizard and editor need: workout days, all sessions with their exercises, recent sets per movement, movements, bodyweight, `is_admin` |
| `POST /api/workout-days` | Create a workout day: `{name, weekday, slots}` |
| `POST /api/workout-days/{id}` | Replace a workout day |
| `POST /api/workout-days/{id}/delete` | Delete a workout day (its sessions are kept) |
| `POST /api/workout-sessions` | Create or replace a session: `{client_id, day_id, cycle, week, date, entries}`. Editing a logged session sends its own `client_id`. `day_id` may be null only for an existing session whose workout day was deleted. |
| `POST /api/workout-sessions/{client_id}/delete` | Delete a session and its exercises |
| `GET /api/trends?days=180` | Per movement: daily best estimated 1RM, or top load for movements logged without RPE |
| `GET /api/movements/normalize?name=...&renaming=...` | Preview the standard form of a new or changed name, and which existing movement it clashes with |
| `GET /api/movements/usage?name=...` | How many logged exercises (all users) and which workout days use a movement (admins) |
| `POST /api/movements/delete` | Delete a movement nobody has logged, removing it from workout days: `{name}`. HTTP 409 with the reason if it has logged exercises or is the only exercise of a workout day (admins) |
| `POST /api/movements` | Create a movement under the standard form of its name: `{name, dip_belt}` (admins) |
| `POST /api/movements/rename` | Rename a movement and/or change its dip belt setting: `{old_name, new_name, dip_belt, merge}`. Answers `confirm_merge` if the new name belongs to another movement and `merge` isn't set (admins) |
| `GET /progress?exercise_name=...&days=...` | Daily best estimated 1RM, for the chart |
| `GET /api/sync`, `POST /api/sync` | Offline cache download, and replay of offline writes |

Validation errors come back as HTTP 422, with a readable message in `detail`.

**HTML fragments (HTMX):**

| Route | Purpose |
| --- | --- |
| `GET /` | The page. For non-admins, the admin-only part between `<!-- BEGIN Admin -->` and `<!-- END Admin -->` is removed. |
| `GET /exercises?offset=&limit=` | Exercise log table with paging |
| `POST /exercises/` | Log one exercise |
| `POST /exercises/{id}/delete` | Delete a logged exercise |
| `GET /movements` | `<option>` list of movements (these lists reload on the `movements-changed` event) |
| `GET /bodyweight`, `PUT /bodyweight` | Show or update bodyweight |
| `POST /recommendations` | Load calculator: estimated 1RM, the load for given reps and RPE, and a form to log it |

## Frontend conventions

- **Theme:** colours are CSS variables on `:root` (`--accent`, `--surface`, `--muted`, ...), with
  dark values applied by `prefers-color-scheme` or by `data-theme="dark"` on `<html>`. Pico's
  variables are overridden on `body`, because Pico defines them on `:root` with more specific
  selectors.
- **Button text colour:** don't use `var(--pico-color)` for text on buttons. Pico sets it to the
  button text colour, which is white. Use `color: inherit`.
- **Decimal fields** (load, RPE, bodyweight) are `type="text" inputmode="decimal"` with
  `data-min`/`data-max`, not `type="number"`. iPhones in regions that use a decimal comma show ","
  on the keypad, and number fields reject it. A script in `index.html` turns commas into dots and
  checks the range.
- **Inputs use at least 16px text**, or iPhone Safari zooms in when they're focused.
- **Hover styles** are switched off on touch screens (`@media (hover: none)`), because they stick
  after a tap.
- **Escaping:** text from users or the database goes through `esc()` in JavaScript and
  `html.escape` in Python before it's put into HTML.
